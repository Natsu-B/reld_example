# 起動コードとスタックのアラインメント

本文の「セクションの配置」の最後で触れた、`_start`をアセンブリで書く理由の説明です。例はreld_exampleの[`nolibc`](../nolibc)ディレクトリのものです。

## 実行開始アドレスと起動コード

`Entry point`はELFヘッダに記録された実行開始アドレスです。リンカは、`ENTRY`に書かれたシンボルのアドレスをここに書きます。本文の`hello`では`0x401000`、つまり`_start`のアドレスになっています。`start.s`の内容をここで確認します。

**start.s**

```asm
.text
.globl _start
.type _start, @function
_start:
    andq $-16, %rsp
    call run
    ud2
```

スタックは関数の戻り先などを保存するためのメモリ領域で、スタックポインタ`%rsp`はその現在の先頭を指すレジスタです。

x86-64 Linuxの呼び出し規約では、`call`の直前に、スタックポインタ`%rsp`を16の倍数にそろえる必要があります。`call`は8バイトの戻り先アドレスをスタックに積むので、通常のC関数は、入口で`%rsp`を16で割った余りが8（`%rsp ≡ 8 (mod 16)`）の状態になります。コンパイラは、この状態を前提に関数のコードを作ります。

一方、`_start`は誰かに`call`されるのではありません。`execve`システムコールでプログラムを読み込んだカーネルが、引数や環境変数をスタックに積んだあと、`Entry point`へ直接ジャンプさせます。戻り先アドレスは積まれないので、`_start`の入口では`%rsp`が16の倍数（`%rsp ≡ 0 (mod 16)`）です。`_start`を通常のC関数として書くと、コンパイラが想定する状態と8バイトずれてしまいます。

そこで入口をアセンブリで書き、`andq $-16, %rsp`で下位4ビットを0にしてから`run`を`call`します。こうすると、`run`は通常のC関数と同じ状態で呼び出されます。この例では開始時から16の倍数なので、`andq`を実行しても`%rsp`の値は変わりません。

`run`は最後に`exit_with`でプロセスを終了します。`ud2`は、`run`が戻ってしまった場合に、不正命令の例外で実行を止めるために置いています。

glibcを使うプログラムでは、`_start`はglibcの`crt1.o`に入っていて、`main`を呼ぶ前にglibcの初期化処理を呼びます。これは本文の「glibcの静的リンク」で見ています。
