# 実行ファイルの書き出しとGNU ldとの比較

本文の「おわりに」で触れた、最後の段階の詳細です。例はreld_exampleの[`glibc`](../glibc)ディレクトリのものです。

## 書き出す内容

最後の段階では、それまでの段階で決めたアドレスや、書き換えたあとのセクションの中身をファイルに書きます。reldの`output::write`は、出力ファイルを必要な大きさで作ってメモリに対応付け（mmap）、次のものを埋めていきます。

1. ELFヘッダ（64バイト）。対象のアーキテクチャ（x86-64）、ファイルの種類（実行ファイルを表す`ET_EXEC`）、実行開始アドレス（`Entry point`）などを記録します
2. プログラムヘッダ（56バイト×本数）。`LOAD`などのセグメントです
3. セクションの中身。参照を書き換えたあとのコードとデータです。`.bss`や`.tbss`はファイル上には書きません
4. セクションヘッダとシンボル表。中身の後ろにまとめて置きます

ファイル上のオフセットは、仮想アドレスとページ内の位置が同じになるように決めます。カーネルはファイルをページ単位でメモリに対応付けるので、例えばアドレス`0x401000`に置くデータは、ファイル上でもページ境界（`0x1000`の倍数）から始まっている必要があります。

## セクションヘッダとシンボル表

カーネルはセクションを見ないので、手順4のセクションヘッダとシンボル表がなくても、プログラムは動きます。それでもreldがこれらを書くのは、`readelf`、`nm`、`objdump`、`gdb`といった道具がこれを頼りにするからです。本文で`objdump -d hello`の出力に`<greet>`のような名前が出ていたのは、reldがシンボル表を書いているおかげです。シンボル表を出力しておくと、自作リンカのデバッグでも、`objdump`や`gdb`で関数名を確かめながら出力を読めます。なお、中身が空の出力セクション（`hello`の`.data`など）は、書き出すときに捨てています。

シンボル表には1つ細かい約束があります。リンカは、TLS変数のシンボルの値に、仮想アドレスではなく**TLSテンプレートの先頭からの位置**を書きます（`counter`なら0）。`gdb`などは、この約束を前提にしています。

## GNU ldとの比較

reldでは、実行結果だけでなく出力したELFの中身も確かめるために、同じ入力をGNU ldでもリンクして、結果を突き合わせるテストを書いています。reld_exampleの`glibc`ディレクトリでは、`make compare`で同じ比較ができます。

**静的glibcのhello_glibcで比べたもの**

| 比べたもの | reld | GNU ld |
|---|---|---|
| 実行結果 | Hello, glibc! counter=42 | Hello, glibc! counter=42 |
| ファイルの大きさ | 811,576バイト | 785,288バイト |
| IRELATIVEの数 | 22 | 22 |

ファイルの大きさの差（約26KB）の大部分は、シンボル表です（文字列表と合わせて約22KB）。reldのほうが多くのシンボルを書き出しています。ほかに、GNU ldは例外処理用の`.eh_frame`の重複をまとめ（約9KB）、同じ文字列定数を1つにまとめ（約2KB）、GOTPCRELXを書き換えてGOTの欄を減らしています。reldはどれもせず、入力をそのままつなげています。逆に、GNU ldだけが出力に残しているセクション（約5.5KBの`.note.stapsdt`など）もあります。

出力はバイト単位では同じにならないので、テストでは、glibcが頼りにしている次のような点が一致するかを確かめています。

- LOCAL以外の定義済みシンボルの集合
- `__init_array_start`から`__init_array_end`までの大きさ
- `__rela_iplt_start`から`__rela_iplt_end`までの大きさと、`.rela.plt`の大きさ

テストは、reld本体の結合テストが49個、ユニットテストが82個です。静的glibcについては、スレッドローカル変数、コンストラクタと`atexit`、IFUNCを使う文字列関数、`errno`などを、実際にリンクして実行しています。
