# セクション配置の細かい規則

本文の「セクションの配置」と「glibcの静的リンク」の「入力セクションのまとめ方」を補う資料です。

## 既定のリンカスクリプトの使用許諾

reldが内蔵している既定のスクリプトは、GNU ldの静的リンク用の既定スクリプトをもとにしています。GNU ldの既定スクリプトには、著作権表示とこの許諾の文を残せば、改変の有無にかかわらず自由に複製・配布してよい、という許諾が書かれています（`ld --verbose`で見られます）。reldのスクリプトにも、この表示を残しています。

## .textと.rodata

`.text`と`.rodata`には、並べ方の決まりはほとんどありません。GCCは、`-ffunction-sections`を付けたときの`.text.関数名`や、起動時にしか使わない関数を入れる`.text.startup`のように、細かい名前のセクションを出します。既定のスクリプトでは、これらを名前の規則で`.text`にまとめ、`.text.unlikely`や`.text.startup`のように使われ方が近いものを寄せて並べています。

`.rodata.str1.1`のような文字列のセクションには、`SHF_MERGE`と`SHF_STRINGS`という属性が付いています。これは「同じ文字列があれば1つにまとめてよい」という印です。GNU ldは実際にまとめますが、reldはまとめずにつなげています。まとめなくても、ファイルが少し大きくなるだけで正しく動きます。

## .initと.finiの中身

`.init`は、`main`の前に呼ばれる`_init`関数を入れるセクションです。`crti.o`と`crtn.o`の`.init`を逆アセンブルすると、次のようになっています。

```console
$ objdump -d -j .init crti.o
0000000000000000 <_init>:
   0:  f3 0f 1e fa             endbr64
   4:  48 83 ec 08             sub    $0x8,%rsp
   8:  48 8b 05 00 00 00 00    mov    0x0(%rip),%rax
   f:  48 85 c0                test   %rax,%rax
  12:  74 02                   je     16 <_init+0x16>
  14:  ff d0                   call   *%rax
$ objdump -d -j .init crtn.o
0000000000000000 <.init>:
   0:  48 83 c4 08             add    $0x8,%rsp
   4:  c3                      ret
```

`crti.o`の`.init`は`ret`がないまま終わっていて、`crtn.o`の`.init`には、`sub`で下げたスタックポインタを戻す`add`と`ret`しかありません。それぞれは関数の前半と後半の断片で、リンカがこの2つをこの順番でつなげて、初めて1つの`_init`関数になります。間に別のファイルの`.init`があれば、それも`_init`の途中に入ります。そうした断片も`ret`を持たない命令の並びとして作られています。そのため`_init`を呼ぶと、CPUは`crti.o`の断片から順に実行し、最後に`crtn.o`の`ret`で戻ります。gccが`.init`を持つファイルのうち`crti.o`をいちばん前に、`crtn.o`をいちばん後ろに渡すのはこのためです。`.fini`も同じ作りです。

既定のスクリプトの`.init : { KEEP(*(SORT_NONE(.init))) }`は、`.init`だけを集めて、コマンドラインの順番のまま並べる指定です。もし`.init`を`.text`の規則で各ファイルの`.text`と一緒に並べてしまうと、2つの断片の間にほかのファイルの`.text`が挟まります。そうなると、`_init`を呼んだCPUは前半の断片を実行したあと、そのまま別の関数のコードを実行してしまいます。

## .tbssとロケーションカウンタ

`.tbss`の扱いには、reldとGNU ldで違いがあります。`.tbss`はテンプレートの一部ですが、実行時にそのアドレスの場所を読み書きするコードはありません。TLS変数を読み書きするコードは、スレッドごとのコピーのほうを使うからです。そこでGNU ldは、`.tbss`にアドレスを割り当てるだけで、ロケーションカウンタを進めません。「glibcの静的リンク」の例を同じ入力でリンクして比べてみます。GNU ldでは`.tbss`の直後の`.init_array`が`.tbss`と同じアドレスから始まっています（GNU ldによるリンクは、reld_exampleの`glibc`ディレクトリの`make gnu`で試せます）。

```console
$ readelf -SW hg_ld   # GNU ldでリンクしたもの
  [Nr] Name         Type       Address          Off    Size
...
  [13] .tdata       PROGBITS   00000000004a5f48 0a4f48 000020
  [14] .tbss        NOBITS     00000000004a5f68 0a4f68 000040
  [15] .init_array  INIT_ARRAY 00000000004a5f68 0a4f68 000008
...
$ readelf -SW hg   # reldでリンクしたもの
...
  [12] .tdata       PROGBITS   00000000004a85e0 0a75e0 000020
  [13] .tbss        NOBITS     00000000004a8600 0a7600 000040
  [14] .init_array  INIT_ARRAY 00000000004a8640 0a7640 000008
...
```

reldは、`.tbss`の分もロケーションカウンタを進めています。実行時には使わないアドレスを0x40バイト分あけてしまいますが、`.tbss`を特別扱いせずに、「`.`はセクションを置くたびに進む」という規則のまま扱えます。どちらでも、`PT_TLS`が表す初期値の大きさ（0x20）と全体の大きさ（0x60）は同じです。

## 複数の規則に合う入力セクション

1つの入力セクションが複数の規則に合うことがあります。既定のスクリプトの`.text`は、次のようになっています。

```
  .text : {
    *(.text.unlikely .text.*_unlikely .text.unlikely.*)
    *(.text.exit .text.exit.*)
    *(.text.startup .text.startup.*)
    *(.text.hot .text.hot.*)
    *(.text .stub .text.*)
  }
```

例えば`.text.startup`は、3行目の規則にも、5行目の`.text.*`にも合います。このときリンカは、**スクリプトで先に書かれた規則**を使います。こうして、起動時にしか使わないコードや、めったに使わないコードを`.text`の中でまとめて置けます。

`/DISCARD/`は特別な出力セクションで、ここに入れたものは捨てられます。reldは`.note.gnu.property`を捨てています。このセクションには「この実行ファイルはCETに対応している」といった性質が書かれていて、複数のファイルの内容を正しく合成しないと実行ファイルの性質を偽ることになります。GNU ldは各ファイルの内容を合成して、出力に`.note.gnu.property`を残します。reldは合成を実装していないので、それまでは捨てるほうが安全だと判断しました。

## 孤児セクション

どの規則にも合わない入力セクションは**孤児セクション**（orphan section）と呼ばれます。reldは、孤児セクションのうち実行時にメモリへ載せないもの（`.comment`など）は出力しません（GNU ldは、これらも出力に残します）。一方、メモリに載せる必要があるものは、どこかに置かなければなりません。

メモリに載せる孤児は、リンカが権限などの属性を見て置き場所を決めます。reldでは、名前の似た出力セクションがあればその後ろ、なければ属性が同じ最後の出力セクションの後ろに置きます。静的glibcをリンクすると、`rodata.cst32`（先頭にドットがありません）と`.stapsdt.base`の2つが孤児になり、読み取り専用の出力セクションの後ろに並びます。

```console
$ readelf -lW hg
...
 Section to Segment mapping:
  Segment Sections...
...
   02     .rodata rodata.cst32 .eh_frame .gcc_except_table .note.ABI-tag .stapsdt.base
```

`--trace mapping`では、孤児に`[orphan]`という印が付きます。

## DATA_SEGMENT_ALIGN

書き込めるデータの前にある`DATA_SEGMENT_ALIGN`は少し変わった関数です。権限を分けるだけなら`.`を次のページ境界に進めればよいのですが、そうすると、ファイルの上でも前のデータの終わりから次のページ境界までを0で埋めることになります。カーネルは、ファイル上の位置と仮想アドレスのページ内の位置がそろっていれば、ファイルのどこからでもページ単位でメモリに対応付けられます（[実行ファイルの書き出しとGNU ldとの比較](output-and-gnu-ld.md)の「書き出す内容」で説明します）。そこでreldは、`.`を次のページに進めたうえで、ページ内の位置は元のまま保つ計算として実装しています。例えば`.`が`0x1234`なら`0x2234`になります（GNU ldは、使うページ数を比べて、もう1つの計算式と使い分けます）。

こうすると、書き込めるデータは、ファイル上では前のデータの直後に詰めて置けます。前のデータの最後と書き込めるデータの最初は、ファイルでは同じページに入ります。カーネルはこのページを、メモリの2つのページに別々に対応付けます。`.`が`0x1234`だった先ほどの例なら、`0x1000`から始まる読み取り専用のページと、`0x2000`から始まる書き込み可能なページです。書き込み可能なほうに書き込んでも、変わるのはそのプロセスのメモリだけで、ファイルやもう一方のページには影響しません。ページの残りを0で埋めなくてよい分だけ、ファイルが小さくなります。静的glibcの例で、書き込めるセグメントが`0x4a85e0`という半端なアドレスから始まっているのはこのためです。

## プログラムヘッダの本数とSIZEOF_HEADERS

スクリプトの最初の行にある`SIZEOF_HEADERS`は、ファイルの先頭に置くELFヘッダとプログラムヘッダを合わせた大きさです。ELFヘッダは64バイトと決まっていますが、プログラムヘッダは1本56バイトなので、本数がわからないと大きさが決まりません。

ところが、プログラムヘッダの本数は、セクションを置いてみるまでわかりません。`LOAD`の本数は、権限の違うセクションがいくつ並ぶかで決まるからです。しかも、`SIZEOF_HEADERS`が変わると、その後ろに置くセクションのアドレスもずれるので、ページの分かれ方が変わることもあります。

そこでreldは、次の手順で本数を決めています。

1. 本数を仮に2本として`SIZEOF_HEADERS`を計算し、セクションを置いてみる
2. 置いた結果から、必要な本数を数える。数えるのは`LOAD`の数と、`GNU_STACK`（スタックの権限を示すヘッダ。reldは実行不可として出力します）の1本、スレッドローカル変数があれば`PT_TLS`の1本
3. 数えた本数が仮の本数と同じなら確定する。違えば、数えた本数を新しい仮の本数にして1に戻る

`hello`では、次のように2回目で確定します。

**helloのプログラムヘッダの本数が決まるまで**

| 回 | 仮の本数 | SIZEOF_HEADERS | 数えた本数 |
|---|---|---|---|
| 1回目 | 2 | 64 + 56 × 2 = 176 | 4（LOAD 3本とGNU_STACK） |
| 2回目 | 4 | 64 + 56 × 4 = 288（0x120） | 4 |

ふつうは2、3回で決まります。ただし、本数が変わるとセクションのアドレスがずれ、それでページの分かれ方が変わって本数がまた変わる、ということが続く可能性もあるので、8回で打ち切ってエラーにしています。
